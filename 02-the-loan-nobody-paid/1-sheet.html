The Loan Nobody Paid

Teacher's sheet · Lesson text (draft)

Overview

Objective: after this, you can tell a safety property from a liveness property by asking whether a violation has a moment, write liveness in TLA+ with eventually (◇), always (□) and leads to (↝), explain why a spec without fairness allows the system to stop (stuttering), add weak fairness for the actions the platform really guarantees and none for crashes, read TLC's liveness counterexample as a lasso, and fix a crash-stranded claim by splitting the job: resume own claims for liveness, an idempotency key at the bank for safety.

Source: none on file. Original course written from general knowledge of TLA+ (Lamport's TLA+, the TLC model checker). Every number below comes from real TLC runs of checks/*.tla (log in checks/tlc-results.txt, regenerated by checks/tlc.sh) and is mirrored by checks/check.py, a Python breadth-first checker with a lasso search, which matches every TLC state count.

Bug: after lesson 1's atomic-claim fix, worker A claims loan 4471 and a deploy restarts its machine. A restarted worker forgets the claim, the other worker leaves claimed loans alone, and the loan sits "claimed" forever. NoDoublePayout still passes: zero transfers is at most one.

Fix: act 2 of the lab: with Crash on and fairness for worker steps, add Resume (a restarted worker finishes loans claimed in its own name) and the loan id as the bank's idempotency key; both NoDoublePayout and EventuallyPaid pass with 2 workers (23 states) and 3 workers (46 states).

Key words: safety property (not "correctness property"), liveness property (not "progress property", "termination"), eventually (not "finally", "at some point" as a term), always, leads to (not "implies eventually" after its definition), stuttering step (not "no-op", "idle step", "pause"), enabled (not "possible", "ready", "available"), weak fairness (not "fair scheduling", "fair scheduler"), lasso (not "cycle" or "loop" alone when meaning the counterexample), idempotency key (not "dedupe key", "request id", "nonce"), lease (not "lock", "timeout"), Crash (the action; "restart" only for the real-world event), Resume (not "recover", "retry"), worker, loan, transfer, payout desk, behavior, step, state, invariant, counterexample, model checker, TLC.

Terms (new in this lesson; lesson 1's terms are reused unchanged):

  • safety property: a property saying nothing bad ever happens; any violation shows up in a finite behavior ending in a bad state. Every invariant is one.
  • liveness property: a property saying something good eventually happens; only a behavior that goes on forever without the good thing violates it.
  • always (□ P): true of a behavior when P is true in every state of it from now on (met in lesson 1's Spec).
  • eventually (◇ P): true of a behavior when P is true in some state of it, now or later.
  • leads to (P ↝ Q): every time P is true, Q is true then or later; means □(P ⇒ ◇Q).
  • stuttering step: a step that leaves every variable unchanged (named in lesson 1, used here). Every TLA+ behavior is infinite; a stopped system takes stuttering steps forever.
  • enabled: an action is enabled in a state when some step of that action can be taken from that state.
  • weak fairness (WF_vars(A)): if A is enabled from some point on forever, A steps keep happening. Formally ◇□(ENABLED ⟨A⟩_vars) ⇒ □◇⟨A⟩_vars.
  • lasso: a liveness counterexample: a path from the start into a loop the behavior repeats forever without the good thing; TLC prints the loop as "Stuttering" (one-state loop) or "Back to state n".
  • idempotency key: a value sent with a request that names it, so the receiver performs it at most once and answers repeats with the same key without acting again.
  • lease (story term, not glossary): a claim with a time limit after which anyone may take it.

Misconception: "the checker passed, so the loan gets paid." Why wrong: an invariant only forbids bad states; a desk that does nothing satisfies NoDoublePayout (the Crash desk passes it in all 10 states while never paying).

Second misconception: "fairness fixes stalls." Why wrong: fairness only pushes enabled actions; after the crash no work is enabled, and fairness is an assumption about the platform (scheduler, supervisor), not code.

Third misconception: "a lease is a lock" / "the worker should remember what it sent." Why wrong: an expired lease does not stop a slow holder (TLC: 5-step double payout); anything the worker remembers, the crash erases (TLC: Resume's 5-step resend).

  2. Lesson 1's fixed desk, Skip only on paid, no crash, no fairness (Live.tla): EventuallyPaid fails; TLC lasso Claim(B), Send(B), Stuttering; 9 states generated, 8 distinct. With weak fairness per worker (LiveFair.tla): no error, 8 distinct states, depth 5.
  3. Crash desk with fairness (Crash.tla, one crash per run): NoDoublePayout holds in all 10 distinct states (13 generated); temporal properties violated with lasso Claim(A), Send(A), Crash(A), Stuttering (transfers 1, the "quiet twin"). With only EventuallyMoney checked, TLC prints Claim(A), Crash(A), Stuttering (transfers 0: Thursday). In an earlier run with only EventuallyPaid in the cfg, TLC printed Claim(B), Crash(B), Stuttering; TLC prints one lasso, not all.
  4. Lasso search in Python (prose snippets 1 and 2, checks/s1.py + checks/s2.py): 10 reachable states; without fairness 7 unpaid states can end a lasso, with fairness 2: ('claimed', ('idle','idle'), 0, True) and ('claimed', ('idle','idle'), 1, True). The search treats stuttering in one state as the only loop, valid because every graph in this lesson is acyclic apart from stuttering (check.py verifies acyclic for every variant).
  5. Lease (Lease.tla, Expire with weak fairness): NoDoublePayout violated after 27 distinct states (44 generated): Claim(A), Expire, Send(A), Claim(B), Send(B), transfers 2. Liveness alone (-config LivenessOnly.cfg): no error, 76 distinct states.
  6. Resume own claims (Resume.tla, owner variable): NoDoublePayout violated after 20 distinct states: Claim(A), Send(A), Crash(A), Resume(A), Send(A), transfers 2. Liveness alone: no error, 29 distinct states.
  7. Fix (IdemKey.tla: atomic Claim, Resume, keys at the bank, Crash, fairness): no error, 25 states generated, 23 distinct, depth 7. Three workers (IdemKey3.tla, Workers overridden in the cfg): no error, 46 distinct states (55 generated), depth 8. Build-it reference (checks/build_it.py): 23 states, none stuck, max transfers 1.
  8. Cliffhanger (ForgetKey.tla, IdemKey plus Forget, which empties the bank's keys): NoDoublePayout violated in 6 steps after 34 distinct states: Claim(A), Send(A), Forget, Crash(A), Resume(A), Send(A).

Concept check, answers (never shown to the learner):

  1. (a) Safety: a violation is a finite behavior ending in a state with two transfers. (b) Liveness: a violation is an infinite behavior (a lasso) in which some approved loan is never paid; no finite prefix shows it. (c) Safety, although it sounds like liveness: once an hour has passed with the loan still claimed, the violation has a moment, and nothing later can repair it. It cannot be written in this lesson's specs because they have no clock; that is lesson 3. Common wrong answer: "liveness, because it says paid".
  2. EventuallyMoney == <>(transfers >= 1) (also accept transfers = 1 or transfers > 0; ◇ over a state predicate about the bank, not the status). The crash desk fails it: TLC (-config MoneyOnly.cfg Crash.tla) prints Claim(A), Crash(A), Stuttering, 10 distinct states. The deciding state is ('claimed', both idle, transfers 0, crashed): Thursday itself. The quiet twin (transfers 1) satisfies it, which is why the two properties differ: EventuallyPaid also demands the books catch up. On the fixed desk (IdemKey.tla) it passes, 23 states. Bonus point if the learner notes that finance needs both.
  3. Yes: LeaseKey.tla (lease + key, no Resume, Crash, fairness including Expire) passes NoDoublePayout, EventuallyPaid and ClaimLeadsToPaid: 134 states generated, 57 distinct, no error. Prefer Resume: a slow worker never triggers a second request, so the bank's key carries less weight (fewer duplicates, and see the 24-hour cliffhanger); no lease duration to tune. Prefer the lease: it does not need the crashed worker to come back under the same name; a worker removed for good by the autoscaler, or renamed on redeploy, strands its claims under Resume, while a lease frees them. (Weak fairness on Resume assumes the worker returns; say so.)

Next bug: the bank keeps idempotency keys for 24 hours. Worker A sends the transfer for loan 4471 on Friday at 17:00, crashes before Mark, and its machine stays down until Monday; it resumes its claim and sends again with key 4471 to a bank that has forgotten the key. TLC (ForgetKey.tla) finds the double payout in 6 steps. Lesson 3: time in a spec (clocks, timeouts, deadlines) and message loss (a reply lost on the way back, so the worker cannot tell whether the request arrived). Recommended course-plan title for lesson 3: "The key the bank forgot" (question: "When the bank forgets keys after a day and replies can be lost, how do you send the money exactly once?").
