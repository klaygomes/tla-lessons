The Payout Desk/Lesson 3/Teacher's sheet

The Key the Bank Forgot

Teacher's sheet · Lesson text (draft)

Overview

Objective: after this, you can put time in a TLA+ spec as an ordinary variable (now) with a Tick action, write a timeout as a guard that switches an action on and a deadline as a guard that switches one off, choose a finite clock (MaxTime) and check that a longer clock does not change the verdict, model a network as a set of messages in flight that may be delivered late or lost, explain why a worker that hears nothing cannot tell a lost request from a lost or late reply, and fix the 24-hour idempotency-key bug with a resend window shorter than the bank's memory, requests the bank refuses after their deadline, and reconciliation that trusts only answers written after the deadline.

Source: none on file. Original course written from general knowledge of TLA+ and TLC. Every number below comes from real TLC runs of checks/*.tla (log in checks/tlc-results.txt, regenerated by checks/tlc.sh) and is mirrored by checks/check.py, a Python breadth-first checker that matches every TLC state count and counterexample length in this lesson.

Bug: lesson 2's fixed desk (Resume plus the loan id as idempotency key). Worker A sends the transfer for loan 4471 on Friday at 17:00 and crashes before Mark; its machine stays down until Monday 09:12; A resumes its claim and sends again with key 4471; the bank keeps keys for 24 hours, so it has forgotten the key and pays a second €50,000.

Fix: act 2 of the lab: with lost and late messages, a running clock and a forgetting bank, the worker asks the bank instead of resending, uses a deadline with a 12-hour window (the bank refuses late requests), and trusts only an "absent" written after its deadline; NoDoublePayout and NoDeadEnd pass with the clock at 48 hours (MaxTime 4) for 2 workers (28,021 states) and 3 workers (54,305 states).

Key words: now (the clock variable; not "time", "timestamp" as a variable name), tick (not "time step", "unit"), Tick (the action), timeout (a guard that switches an action on; not "expiry" as a term), deadline (a guard that switches an action off; not "cutoff", "expiry"), window (the ticks from claim to deadline in which resending is allowed; not "grace period"), constant (not "parameter"), MaxTime, TTL ("time to live"; not "retention"), message (not "packet", "event"), in flight (not "pending", "queued"), lost (the event; Drop is the action; not "dropped" as an adjective in prose), reply (not "response"), answer (the bank's reply to a question: found or absent), reconcile (asking the bank after the deadline; not "verify", "check" as a verb, because Check was lesson 1's action), Lookup, AskBank, Answer, Deliver, Drop, Retry, GotOk, GotAbsent (the actions), NoDeadEnd. Reused unchanged: worker, loan, transfer, payout desk, behavior, step, state, invariant, counterexample, enabled, safety property, idempotency key, Resume, Crash.

Terms (new in this lesson):

  • now: a variable holding the current time as a whole number of ticks; one tick is 12 hours in this lesson.
  • Tick: the action that adds one to now and changes nothing else; time passes only by Tick steps.
  • discrete clock: a clock that jumps from tick to tick; enough when the question is which side of a line a step falls on.
  • constant: a name the spec leaves open, filled in by the configuration file (MaxTime, TTL, Window).
  • MaxTime: the last tick the model's clock may reach; keeps the state space finite and hides any bug that needs more time.
  • timeout: a guard on now that switches an action on after some time (Forget(k) once now ≥ stored time + TTL); enabled, never forced, so it models "at least".
  • deadline: a guard on now that switches an action off after some time (Send and Retry only while now ≤ deadline).
  • message: a value one party puts in the network for another to take out later; modelled as a record in the set net.
  • in flight: a message in net, not yet delivered or lost.
  • lost: a message removed from net without being delivered (the Drop action).
  • record: a value with named fields, [kind |-> "pay", by |-> 1]; m.kind reads a field.

Misconception: "a timeout means the request failed." Why wrong: a timeout only means the worker stopped waiting; TLC's Lossy counterexample (9 steps) loses nothing, the reply is merely late.

Second misconception: "if the bank says absent, the money did not move." Why wrong: the answer describes the bank when it was written; a request in flight can pay after that (Ask, 11 steps). "Absent" means "never" only when no request that could still pay is in flight.

Third misconception: "the model passed, so it is right." Why wrong: it passed for the clock it was given; Clock passes at MaxTime 1 and FixStale passes at MaxTime 3 (same 8,288 states as Fix), and both pay twice with a longer clock.

Fourth misconception: "the worker's deadline is enough." Why wrong: the worker controls when it sends, not when the request lands; FixNoRefuse pays twice in 9 steps although every send is inside the window.

Worked examples (TLC runs, mirrored by check.py):

  1. The weekend by hand (Clock, TTL 2): Claim(A), Send(A) at tick 0 storing (4471, 0), Crash(A), Tick, Tick, Forget at tick 2, Resume(A), Send(A) storing (4471, 2): 8 steps, transfers 2. Forget is not enabled at tick 1. Python replay in the prose prints 1 {(4471, 0)} 1, 2 set() 1, 2 {(4471, 2)} 2. TLC's own trace has the same 8 steps with the crash after Forget.
  2. Two worlds (the lost request and the lost reply): Claim(A), Send(A), then Drop of the request (transfers 0) or Deliver then Drop of the "ok" (transfers 1); worker A's view (its pc "waiting", no replies) is identical. This is a hand example in the prose's Python, not a separate TLC run; both behaviors are allowed by Lossy.tla (Send, Deliver, Drop are its actions).
  3. Lossy with TTL 2: double payout in 9 steps, no Drop: Claim(A), Send(A), Deliver, Tick, Tick, Forget, Retry(A), Send(A), Deliver.
  4. Ask over the network: double payout in 11 steps: Claim(A), Send(A), AskBank(A), Answer ("absent" before the request lands), Deliver, Tick, Tick, Forget, GotAbsent(A), Send(A), Deliver.
  5. Fix: 28,021 states (MaxTime 4), no error; three breakages: Window 2 (9 steps), FixNoRefuse (9 steps), DeadlineOnly (NoDeadEnd violated in 3 steps), FixStale (passes at MaxTime 3, 17 steps at MaxTime 4).

Concept check, answers (never shown to the learner):

  1. No, the bug is only out of reach. The weekend needs now to reach the key's stored time plus TTL, tick 6, so MaxTime 3 cannot contain it: TLC (-config ClockTTL6.cfg Clock.tla) passes with 188 distinct states. With MaxTime 6 (ClockTTL6Long.cfg) TLC finds the double payout in 12 steps (Claim, Send, six Ticks, Forget, Crash, Resume, Send; 508 distinct states when it stopped). Rule: the clock must run at least past the longest timeout in the spec, and the verdict should be rechecked with a longer clock. Common wrong answer: "yes, 72 hours covers a weekend" (it covers this one; the model must still be able to reach it, and a longer outage still breaks it).
  2. The assumption: Lookup reads the bank's ledger and decides in one atomic step, so the answer is current when the worker acts on it. A real worker asks over a network, and the answer can be stale by the time it is read. Ask.tla shows it: the bank answers "absent" before the payment request lands, the request then pays, and the worker acts on the old "absent" a day later (11 steps). Accept "the network is perfect / instant" as the assumption if the learner names the stale answer.
  3. A payment, once made, stays made: the bank's ledger never forgets, so "found" or "ok" is true forever after it is written. "Absent" is true only until a request in flight lands. After the worker's deadline, the bank refuses every request of that window, so an "absent" written after the deadline stays true; one written before it may not (FixStale: 17 steps with MaxTime 4). Bonus if the learner notes that the check is against the current window's deadline.
