The Payout Desk/Lesson 5/Teacher's sheet

Writing the Worker as Code

Teacher's sheet · Lesson text (draft)

Overview

Objective: after this, you can write a worker as a PlusCal algorithm (algorithm, variables, process and process variables, labels, :=, if, await, either/or, with, goto), translate it with pcal.trans and read the generated TLA+ (one action per label, pc, Done, Terminating, Termination), explain that labels set atomicity (everything between two labels is one step), choose fair process or fair+ process (weak or strong fairness) knowing what each promises about the platform, and place labels by the rule "one label per real interaction with shared state".

Source: none on file. Original course written from general knowledge of TLA+, PlusCal and the TLC model checker. Every number below comes from real runs in checks/ (tlc.sh regenerates tlc-results.txt: 21 translations, 29 TLC runs, 5 of them with -continue) and is mirrored by checks/check.py (breadth-first checker with a fairness-aware lasso search) where noted.

The same week she moves the TypeScript to a data layer that loads the row and saves it back: two database calls. The spec now describes a desk she no longer runs; lesson 1's race is back, and only the bank's idempotency key (lesson 2) stops the duplicates, which finance sees as a jump in refused duplicate requests.

Fix: act 2 of the lab: switch the code back to one conditional update and place the labels one per real interaction (claim | send | mark: check and claim together); the checker passes with 2 workers (12 states) and 3 (32 states). The honest spec of Noor's two-call code fails in 6 steps; Noor's original spec passes but does not match her code.

Key words: PlusCal (not "Pluscal", "PCal" in prose), algorithm, process (not "thread"; "worker" stays the story noun, "process" the PlusCal one), process variable (not "local", "private variable" as a term), label (not "checkpoint", "step marker"), step, translator (not "compiler", "transpiler"; the tool is pcal.trans), translation, pc, Done, Terminating, Termination, await (not "wait for", "block on" as terms; "waits" fine as a verb), either/or (not "nondeterministic choice" as a term after first use), with, goto, real interaction (not "side effect", "I/O", "round trip" as the term; "round trip" fine as a gloss), honest (spec matches code; not "faithful", "accurate"), weak fairness / fair process, strong fairness / fair+ process (not "strict fairness", "fair plus"), enabled, lasso, worker, loan, transfer, invariant, counterexample, TLC.

Terms (new in this lesson; lessons 1 to 4 terms reused unchanged; weak fairness, strong fairness, enabled, lasso, EXCEPT and the idempotency key are recaps, not new):

  • PlusCal: an algorithm language that is translated into TLA+; you write a worker as a program instead of writing its actions by hand.
  • algorithm: the PlusCal program, written inside a comment in the module, (* --algorithm Name { ... } *).
  • process: one running copy of a block of code; process (w \in Workers) runs one per worker; inside, self names the process. process (r = "recon") is a single process.
  • process variable: a variable declared under a process (variable mine = 0;), private to each process; translated into a function from processes to values.
  • label: a name before a statement (claim:); marks where a step begins. Everything from one label to the next is one step.
  • translator: pcal.trans, which writes the TLA+ translation between the BEGIN and END TRANSLATION lines of the same file.
  • await: a guard; the label's step can happen only in states where the condition holds (an unprimed conjunct of the action).
  • either/or, with: choices; the checker tries every branch / every element. Translated to ∨ and ∃.
  • goto: jumps to a label; ends the step, so whatever follows belongs to a later one; goto Done finishes the worker.
  • deadlock: a state with no possible next step; TLC reports it unless run with -deadlock (lesson 1 only used the flag). Terminating exists so a finished desk is not a deadlock; an empty with or a false await for every worker is.
  • Termination: the liveness property the translator always defines, ◇(every process is at Done); checked only when listed on a PROPERTY line.
  • real interaction (story term, not glossary): one call that reads or changes state another process or system can see (a SQL statement, a bank request, a queue message).
  • the rule: one label per real interaction with shared state.

Misconception: "TLC passed, so the code is safe." Why wrong: TLC checked the spec; Noor's one-label spec is safe (12 states) but describes a one-statement claim, and her code makes two calls; the honest spec fails in 6 steps.

Second misconception: "more labels is always safer." Why wrong: over-splitting a single SQL statement gives a counterexample for a race the code does not have (the 4-label placement on the conditional-update code) and more states (34 vs 12); aim for honest.

Third misconception: "fair makes the worker eventually do anything it can do." Why wrong: weak fairness covers only continuously enabled steps; a worker waiting for a shared line that flickers can wait forever (Line: lasso), and fair+ is a promise about the platform (a pool that does not skip a waiter forever), not a fix. "What people get wrong" on the page: more labels is always safer; the checker passed, so the code is safe (lesson 7 ties code to spec); PlusCal is a different language (it is TLA+; read the translation).

Concept check, answers (never shown to the learner):

  1. Not honest. bank.transfer and db.setStatus are two real interactions with two different systems, so the spec needs a label between them (Place010.tla passes with 8 states, but that pass says nothing about the code). What it can never show: a state where the money has gone and the loan is not marked yet. That is exactly where lesson 2's crash lands (the quiet twin): add a crash and the merged spec has no place for it to happen between the two calls, so it would never find a resend after a crash between them, or a loan stuck "claimed" with the money sent. It passes safety here only because the race lives in the claim. Common wrong answer: "it passes, so it's fine" or "it's safe because the send happens once".
  2. A label is one step and one step is one TLA+ action, in which status' has a single value; "claimed, then paid" inside one step is a state nobody could observe. PlusCal requires a label before a variable is assigned a second time (the translator's "Missing label", observed on Place000.tla and Place100.tla). Where to put labels depends on the code, not on the translator: with the conditional update, claim | send | mark (labels before the claim, the transfer and the mark; OneLabel.tla); with find + save, check | claim | send | mark. Bonus: Python's merge composes the same functions without complaint; the refusal is about steps.
  3. Weak fairness promises a step only for an action enabled from some point on forever. In the lasso the line is busy in every other state, so the waiting worker's send keeps switching off and weak fairness makes no promise (TLC: Line.tla violates EventuallyPaid with the lasso claim, take, give, back to take). fair+ (strong fairness) needs only "enabled again and again", which holds, and TLC passes (LineStrong.tla, 14 states). Before writing fair+, the real pool must guarantee that a waiting worker is not skipped forever, for example by serving waiters in order. If whoever asks fastest wins, fair+ describes a pool you don't run.
