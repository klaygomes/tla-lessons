# Does the Code Match the Spec?

Objective: after this, you can write a system's purpose as a small abstract spec (PayOnce, one step), write a refinement mapping from a detailed design to it with `INSTANCE … WITH`, check the refinement in TLC as `PROPERTY Refines` with `Refines == Abstract!Spec`, explain why stuttering steps make refinement possible, read a refinement failure (a forbidden step with its abstract column, or a lasso against the abstract spec's fairness), and explain why refinement carries liveness only when the abstract spec includes fairness and the design makes fairness promises of its own.

Terms (new in this lesson; earlier terms reused unchanged):
- abstract spec: a smaller spec that says what a system does and leaves out how; here PayOnce, two variables, one action, two states.
- refinement mapping: for each variable of the abstract spec, an expression over the design's variables saying what it means; here status ← PaidAtBank (paid once the bank has made a transfer), transfers ← transfers.
- refines: a design refines an abstract spec when every behavior of the design, translated state by state through the mapping, is a behavior the abstract spec allows (first state satisfies its Init, every step is one of its steps or a stuttering step, its fairness holds). In TLA+: `Spec => Abstract!Spec`.
- INSTANCE … WITH (notation): brings in a module with each of its variables replaced by an expression; `A!F` names definition F of instance A. Same-named variables are substituted implicitly.
- (reused, given a new role) stuttering step: a step of the design that leaves the mapped abstract variables unchanged is a stuttering step of the abstract spec.

Misconception: "the checker passed my properties, so the design does what it should." Why wrong: the pilot passed NoDoublePayout and TablePaid in all 60 states and the money never moved; properties are the ones you thought of, refinement brings every property of the abstract spec.
Second misconception: "the mapping is a detail; map status to status." Why wrong: the identity mapping fails a correct design (step 3, Confirm) and the Liar mapping (transfers ← table says paid) makes the broken pilot pass in 60 states; the mapping is half of the claim.
Third misconception: "refinement is a safety check." Why wrong: the pilot and the no-lease-fairness design pass the step half (RefinesSafety) and fail Refines only through PayOnce's WF_avars(Pay); drop that WF and they pass.
"What people get wrong" on the page: refinement is one more invariant; the mapping is a detail (Liar, with TLA+, read-aloud and Python); the design refines PayOnce so the service is correct (the TypeScript is a further level, as in lesson 5; 2 and 3 workers only, lesson 8).

Concept check, answers (never shown to the learner):
1. Step 7, Confirm(B): (paid, 1) → (paid, 1), a stuttering step, because the bank already holds key 4471 and transfers stays 1. Without the key it would be (paid, 1) → (paid, 2), neither Pay (status was not approved) nor stutter: a forbidden step, exactly the last step of the NoKey trace. Step 9, Mark(B): a stutter; Mark changes status, queue and pc, none of which PaidAtBank reads. Common wrong answer: "Mark(B) is a second Pay because it writes paid".
2. Only the design without keys still fails: its failure is a forbidden step, in the step half. The pilot (`-config SafetyOnly.cfg MarkFirst.tla`: no error, 60 states), the design with no fairness on Expire (`-config SafetyOnly.cfg NoLease.tla`: no error, 99) and the good design through the always-"approved, 0" mapping (`TrivialSafety.cfg`: no error, 99) all pass, because their only failure was a lasso against WF_avars(Pay). With the WF, the always-approved mapping fails (`Trivial.cfg`, temporal properties violated; the printed lasso varied between runs, e.g. Receive(A), Send(A), Confirm(A), Expire, Receive(B), Crash(B), Mark(A), Stuttering). Point: without fairness in the abstract spec, a mapping that says nothing ever happens refines anything.
3. Mapping: `PaidAtBank == IF transfers > 0 THEN "paid" ELSE "approved"`, `Abstract == INSTANCE PayOnce WITH status <- PaidAtBank, transfers <- transfers`. It refines PayOnce, both halves: `IdemKeyRefines.tla`, no error, 25 generated, 23 distinct, depth 7 (the same 23 states as lesson 2). The Pay step is the first keyed Send; the resend after Resume is a stutter. Accept answers that predict the identity mapping fails because lesson 2's status takes the value "claimed", which PayOnce never has (reasoning, not run).
