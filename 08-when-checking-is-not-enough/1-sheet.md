# When Checking Is Not Enough

Objective: after this, you can explain why model checking a small number of workers is not evidence for every number, state the three conditions for an inductive invariant (Init ⇒ Inv, Inv ∧ Next ⇒ Inv′, Inv ⇒ the property), check inductiveness with TLC by starting from every TypeOK state that satisfies the candidate (INIT Inv, NEXT Next, INVARIANT Inv), read a counterexample to inductiveness and, before strengthening, check the candidate on reachable states from Init (a candidate the desk itself breaks cannot be strengthened), strengthen NoDoublePayout until it is inductive, and give the per-action argument that makes the result hold for any number of workers.

Terms (new in this lesson; earlier terms unchanged):
- inductive invariant: a state property Inv such that every initial state satisfies it and every step from any state satisfying it leads to a state satisfying it; it then holds in every reachable state.
- counterexample to inductiveness (CTI): a state satisfying the candidate plus one step to a state that does not; its first state need not be reachable.
- strengthen: add a conjunct to a candidate so that it excludes more states (only states the desk never reaches, or the candidate becomes false).
- type invariant (TypeOK): a formula giving each variable a finite set of sensible values; here it is the board TLC enumerates starting states from.
- (TLA+ notation new here: priming a whole formula `Inv'`, `[Workers -> Pcs]` set of functions, `0..2`, `Cardinality` from FiniteSets, `EXTENDS` of the spec's own module, cfg lines `INIT` and `NEXT`, `[][StepKeeps]_vars` on a PROPERTY line. Recaps, not new: `=>` (lesson 6), `\A` (lesson 2), `THEOREM` (lesson 7), `{w \in S : P}` (explained again in the prose), `INVARIANT`, `CONSTANT`, `|->`.)

Misconception: “it’s an invariant, so it’s inductive.” Why wrong: NoDoublePayout holds in all reachable states but has 21 CTIs with 2 workers, all from unreachable states.
Second misconception: “TLC passed the inductive check, so it holds for 300.” Why wrong: TLC checked N = 2..5; the generalisation is the per-action argument, which never mentions N.
Third misconception: “a CTI is a bug.” Why wrong: most CTIs start from unreachable states; only when the CTI's first state is reachable is the desk at fault.
Fourth misconception: “stronger is always safer.” Why wrong: FALSE passes the inductive check from 0 states, and OnlyOneBusy is false on a reachable state.

Concept check, answers (never shown to the learner):
1. `TypeOK /\ (transfers = 0)`: InitHolds yes (start has 0 transfers); InvEnough yes (0 ≤ 1); StepKeeps no: any Send makes transfers 1. Its CTIs include reachable first states, e.g. (claimed, A claimed, B idle, 0) → Send(A); so it is not merely too weak, it is false on reachable states ((claimed, A sent, B idle, 1) is reachable). `diagnose` returns “not an invariant”. Note the Python search lists the unreachable (approved, idle, claimed, 0) first; the learner should look for a reachable one. Python obligations: (True, False, True).
2. The candidate is `status \in {"approved", "claimed", "paid"}`. It is inductive and holds initially but fails condition 3: it says nothing about transfers, so it does not imply NoDoublePayout (Python obligations of a candidate true everywhere: (True, True, False)). An inductive invariant only proves what it implies. (Bonus, reasoning only, not run in TLC: with TLC, the inductive run would also need TypeOK to enumerate, and TypeOK’s 0..2 bound would make TLC report a step to transfers 3; the mathematical point stands.)
3. The per-action argument: every step is one worker doing Claim, Send, Mark or Skip, and each case only reads the status, the transfer count and the number of claims, changing each by at most one; nothing depends on N. If one step could move two workers (two Claims at once, or two Sends), the Claim row (“now 0 + 1 = 1”) or the Send row (“sum unchanged”) would break: two claims at once would make the budget 2.
